# AtelierData — independent Ghidra IDF reference-site audit (2026-10-31)

## Purpose and implementation

New `ghidra_idf_reference_site_audit.py` reads an authorized, private PE32
executable and the private/public reports produced by
`AtelierData_IDF_Xrefs_Verified.java`. It first invokes the existing
SHA256-bound `ghidra_idf_xref_verify.verify`, which independently checks the
literal bytes and public/private evidence consistency. The new pass maps
each *reported reference source address* to the original PE32 section table
and classifies it as file-backed executable, file-backed non-executable,
unmapped, or ambiguously mapped. It also counts exact little-endian literal
virtual-address bytes within a bounded 16-byte window after a mapped
executable reference site.

These are **raw mapping and byte-level observations**. A nearby address is
not a verified instruction, code reference, caller, data loader, or decoder.
Ghidra's instruction boundaries and reference database are not reproduced
independently. The output deliberately contains no original bytes, literal
locations, source addresses, or proprietary content. Reports are bounded
by the existing private/public Ghidra verifier.

The nine regression tests use only synthetic PE32 fixtures, including
a positive raw pointer match, a negative raw match, an unmapped source,
a non-executable source, a duplicate source, invalid addresses, modified
SHA256, modified aggregate evidence and input immutability. The Windows
workflow discovers `test_*.py` automatically.

## Reproducible private invocation

```powershell
python projects/atelierdata/ghidra_idf_reference_site_audit.py `
  --pe C:\PRIVATE\ADBCD.exe `
  --expected-sha256 a505bbc4f8678713f352faa8fc70337d9edbe5e0ebd23ba305ca3bccd0f6fce4 `
  --private-ghidra C:\PRIVATE\idf-xrefs-private.json `
  --public-ghidra C:\PRIVATE\idf-xrefs-public.json `
  --output C:\PRIVATE\idf-reference-sites-aggregate.json
```

The private Ghidra reports must be generated by **actually running** the
Ghidra script on the authorized original. Their existence is not assumed.
Do not publish the original PE or private reports. This script never
executes or modifies the original and never touches activation/licensing.

## Independent archive listing cross-check

The owner's private Google Drive folder contains `INVENTAR.txt` and
`listare_7z.txt`. A read-only metadata comparison performed on 2026-10-31
found 139 paths in each, 0 missing paths, 0 extra paths and 0 size
mismatches. All 139 listed file entries have RAR CRC metadata. The
uncompressed inventory totals 2,323,704,957 bytes, including 81 `.IDF`
entries totaling 2,231,509,692 bytes. The listing identifies a single,
non-encrypted, non-multivolume RAR5 archive. This is a **cross-check of two
textual inventory records**, not a fresh SHA256 hash of the original RAR
or its members and not a vendor-authenticity finding.

The listing names architecture-specific install scripts, Sentinel
redistributables and Visual C++ redistributables, but it does not identify
an authenticated Autodata MSI or vendor setup installer. Activation and
emulation tool names also appear in the inventory. Filename evidence alone
cannot establish their behavior or maliciousness. No original executable,
installer or potentially unsafe tool was run. The Google-blocked package
0016 was not fetched, opened, bypassed or extracted.

## Current limitations and next evidence gate

No new Ghidra or REA execution against the private original was possible
from this environment because the original PE and private Ghidra JSON
reports are not directly accessible as individual files. The previously
documented REA observations and 43 raw IAT candidates remain unconfirmed
by Ghidra disassembly. No `.IDF` loader, record schema, encryption
mechanism or decoder has been proven.

The next evidence gate is to run the existing SHA256-bound Ghidra xref
script in an authorized private environment, then feed its private/public
JSON reports to the new independent reference-site audit. Investigate
actual functions and dynamic file-API resolution only after validating
those references; never infer a loader from raw string matches alone.
